## ADR-001: Использование PostgreSQL 18 в качестве основной СУБД

### Статус
Принято

### Контекст
Проект ReadMe — учебная платформа с курсами, пользователями и связанными данными (записи на курсы, прогресс, материалы). Требуется надёжное реляционное хранилище с поддержкой сложных запросов, транзакционной целостностью и хорошей экосистемой инструментов. Рассматривались: PostgreSQL, MySQL, SQLite, MariaDB.

### Решение
Выбран PostgreSQL 18 (образ `postgres:18.3-alpine3.23`).

**Почему PostgreSQL:**
- Полная поддержка ACID-транзакций и SAVEPOINT — критично для тестирования (изоляция тестов через вложенные транзакции).
- Богатый набор типов данных (JSONB, UUID, массивы) и расширений (pg_stat_statements).
- Зрелая экосистема: Alembic для миграций, asyncpg / psycopg для async-драйверов, SQLAlchemy как ORM.
- PostgreSQL 18 содержит улучшения планировщика запросов и производительности по сравнению с предыдущими версиями.

**Конфигурация prod-окружения:**
- `shared_buffers=1GB`, `effective_cache_size=4GB`, `work_mem=16MB` — настройки под реальную нагрузку.
- `statement_timeout=60s`, `idle_in_transaction_session_timeout=10s` — защита от зависших транзакций.
- `pg_stat_statements` — мониторинг медленных запросов.

### Последствия

**Позитивные:**
- Надёжная транзакционная модель упрощает тестирование (SAVEPOINT-изоляция в pytest).
- Гибкая схема мигрирования через Alembic.
- Встроенный мониторинг производительности через `pg_stat_statements`.

**Негативные / риски и их смягчение:**
- *PostgreSQL 18 — относительно новая версия*: возможна нестабильность некоторых расширений.
  → Смягчение: используется `alpine`-образ с фиксированной версией (`18.3-alpine3.23`), изменения версии — только через явное обновление образа.
- *Ресурсоёмкость* при большом числе соединений.

## ADR-002: Использование Redis в качестве кеша и хранилища сессий

### Статус
Принято

### Контекст
Приложению необходимо хранить краткосрочные данные с истечением TTL: JWT refresh-токены (инвалидация, blacklist), пользовательские сессии, потенциальное кеширование часто запрашиваемых данных. Синхронный доступ к PostgreSQL для каждой проверки токена создаёт лишнюю нагрузку.

### Решение
Выбран Redis 7.4 (образ `redis:7.4.8-alpine3.21`) в роли in-memory хранилища с персистентностью.

**Как используется:**
- Хранение refresh-токенов с TTL, соответствующим `TOKEN_EXPIRE` из конфигурации.
- Потенциальный blacklist отозванных JWT access-токенов.
- Доступ через асинхронный клиент (совместим с asyncio-стеком FastAPI).
- Конфигурационный файл `redis.conf` монтируется как `read-only` volume — управление параметрами вынесено из командной строки.
- Пароль передаётся через переменную окружения `REDIS_PASSWORD`.

### Последствия

**Позитивные:**
- Проверка токенов O(1) без обращения к PostgreSQL.
- Автоматическое истечение сессий через TTL без фоновых job-ов.
- Минимальные задержки (sub-millisecond) для операций аутентификации.

**Негативные / риски и их смягчение:**
- *Потеря данных при рестарте без персистентности.*
  → Смягчение: volume `readme-redis-database-data` обеспечивает сохранность при перезапуске контейнера.

## ADR-003: Использование Python 3.13 в качестве языка реализации

### Статус
Принято

### Контекст
Команда владеет Python. Необходима современная версия с поддержкой asyncio, актуальными библиотеками (FastAPI, SQLAlchemy 2.x, pytest-asyncio) и улучшениями производительности. Рассматривались: Python 3.11, 3.12, 3.13.

### Решение
Выбран Python 3.13.

**Почему 3.13:**
- Улучшения производительности интерпретатора (incremental GC, оптимизации компилятора байт-кода).
- Совместимость со всем используемым стеком: FastAPI, SQLAlchemy 2.x, asyncpg, redis-py, pytest-asyncio.

**Инструменты:**
- `ruff` (конфигурация `ruff.toml`) — линтер и форматтер.
- `pytest` с `pytest.ini` и `.coveragerc` — тестирование с измерением покрытия.

### Последствия

**Позитивные:**
- Актуальная типизация и производительность из коробки.
- Поддержка LTS до ~2028 года.

**Негативные / риски и их смягчение:**
- *Некоторые сторонние пакеты могут запаздывать с поддержкой 3.13.*
  → Смягчение: зависимости фиксируются в `requirements.txt` / `pyproject.toml` с конкретными версиями.

## ADR-004: Использование FastAPI в качестве веб-фреймворка

### Статус
Принято

### Контекст
Серверная часть проекта — REST API. Требования: высокая производительность, нативный async, автоматическая валидация запросов/ответов, автогенерация документации. Рассматривались: FastAPI, Django REST Framework, Flask.

### Решение
Выбран FastAPI.

**Почему FastAPI:**
- Нативная асинхронность (ASGI) — согласуется с async SQLAlchemy и async Redis-клиентом.
- Автоматическая валидация через Pydantic v2.
- Автогенерация OpenAPI/Swagger — документация актуальна всегда.
- Dependency Injection из коробки — чистое внедрение зависимостей (сессии БД, текущий пользователь, Redis).
- Встроенная поддержка `HTTPException` и middleware.

**Сервер:** Uvicorn (ASGI), порт задаётся через `SERVER_PORT` (по умолчанию `8080`).

### Последствия

**Позитивные:**
- Строгая типизация API-контракта снижает число ошибок интеграции клиент-сервер.
- Dependency Injection упрощает тестирование — зависимости переопределяются через `app.dependency_overrides`.

**Негативные / риски и их смягчение:**
- *Pydantic v2 — существенные изменения по сравнению с v1.*
  → Смягчение: версия Pydantic фиксирована; команда придерживается v2-синтаксиса.

## ADR-005: Использование SQLAlchemy 2.x в качестве ORM

### Статус
Принято

### Контекст
Необходим инструмент для работы с PostgreSQL из Python: описание схемы, формирование запросов, управление соединениями. Требования: поддержка asyncio, совместимость с Alembic для миграций, SAVEPOINT для изоляции тестов.

### Решение
Выбран SQLAlchemy 2.x (async режим через `AsyncSession` / `create_async_engine`).

**Как используется:**
- Декларативные модели (`DeclarativeBase`) — описание схемы таблиц в Python.
- `AsyncSession` + `AsyncEngine` — все запросы асинхронны, не блокируют event loop.
- `SAVEPOINT` (`session.begin_nested()`) — изоляция тестов: каждый тест оборачивается во вложенную транзакцию и откатывается без сброса схемы.
- Alembic (`alembic.ini`) — автогенерация и применение миграций; применяются автоматически при старте (сервис `auto-migrations`).

**Альтернативы, отклонённые:**
- `Tortoise ORM` — менее зрелая экосистема, слабее интегрирована с Alembic.
- Чистый `asyncpg` — слишком низкоуровневый, нет ORM.

### Последствия

**Позитивные:**
- Миграции через Alembic полностью автоматизированы в CI/CD.
- SAVEPOINT-изоляция в тестах: база не пересоздаётся между тестами — тесты быстрые.
- Выразительный query API (2.x `select()` стиль) вместо устаревшего `session.query()`.

**Негативные / риски и их смягчение:**
- *Async SQLAlchemy требует аккуратного управления жизненным циклом сессии.*
  → Смягчение: сессия передаётся через FastAPI Dependency; закрывается в блоке `finally`.

## ADR-006: Клиент-серверная архитектура с разделённым фронтендом

### Статус
Принято

### Контекст
Проект предоставляет учебную платформу конечным пользователям. Необходимо определить: монолит с серверным рендерингом или разделённые клиент и сервер.

### Решение
Принята клиент-серверная архитектура: отдельный клиент и отдельный сервер.

**Как реализовано:**
- `client` — самостоятельный сервис (собственный Docker-образ `readme-client`), отдаёт статику пользователю.
- `server` — REST API, не знает о клиенте; общение только через HTTP.
- Клиент зависит от готовности сервера (`depends_on: server: condition: service_healthy`).
- Оба сервиса в одной Docker-сети `readme-network` (bridge); клиент обращается к серверу по имени сервиса внутри сети.

**Язык клиента:** JavaScript + HTML/CSS + Python 3.13 Jinja.

### Последствия

**Позитивные:**
- Независимое масштабирование клиента и сервера.
- Сервер можно использовать как API для мобильных клиентов или сторонних интеграций в будущем.
- Чёткое разделение ответственности: бизнес-логика только на сервере.

**Негативные / риски и их смягчение:**
- *Усложнение деплоя*: два образа вместо одного.
  → Смягчение: Docker Compose объединяет оба сервиса.

## ADR-007: Контейнеризация через Docker, Docker Compose и Docker Volumes

### Статус
Принято

### Контекст
Проект включает несколько сервисов: PostgreSQL, Redis, сервер, клиент, сервис бэкапов, сервис миграций. Необходимо обеспечить воспроизводимость среды и простоту развёртывания.

### Решение
Каждый сервис упакован в отдельный Docker-образ. Оркестрация через Docker Compose с двумя файлами конфигурации:
- `docker-compose-dev.yml` — для локальной разработки.
- `docker-compose-prod.yml` — для production-деплоя.

**Volumes (именованные):**
- `readme-postgres-database-data` — данные PostgreSQL (персистентность).
- `readme-postgres-database-backups` — автоматические бэкапы (доступны из `database-manager`).
- `readme-redis-database-data` — персистентность Redis (AOF/RDB).
- `readme-courses-resources` — загружаемые материалы курсов (shared между сервером и возможным CDN).

**Сеть:** `readme-network` (bridge) — все сервисы видят друг друга по имени контейнера.

**Порядок запуска через `depends_on` + healthcheck:**
1. `postgres-database` + `redis-database` (healthcheck).
2. `auto-migrations` (применяет Alembic-миграции, `restart: no`).
3. `server` (ждёт `auto-migrations: service_completed_successfully`).
4. `client` (ждёт `server: service_healthy`).

**Лимиты ресурсов** явно заданы для каждого сервиса (CPU + memory).

**Логирование:** `driver: json-file`, `max-size: 10m`, `max-file: 3` — ротация логов без внешнего log-агента.

### Последствия

**Позитивные:**
- Именованные volumes переживают пересоздание контейнеров.
- `restart: unless-stopped` — автовосстановление сервисов после падения.
- Изолированная сеть — сервисы недоступны извне, кроме явно опубликованных портов.

## ADR-008: Alembic для управления миграциями схемы БД

### Статус
Принято

### Контекст
Схема PostgreSQL эволюционирует по мере разработки. Необходим инструмент для версионирования и применения изменений схемы без ручного SQL и без потери данных.

### Решение
Выбран Alembic (конфигурация в `alembic.ini`). Миграции применяются автоматически при каждом деплое через отдельный сервис `auto-migrations` в Docker Compose.

**Как работает:**
- `alembic revision --autogenerate` генерирует миграцию из diff между моделями и текущей схемой БД.
- В prod: сервис `auto-migrations` (`command: ["migrate", "auto"]`) запускается до старта сервера, применяет все pending-миграции и завершается (`restart: no`).
- Сервер стартует только после `auto-migrations: service_completed_successfully`.

### Последствия

**Позитивные:**
- Zero-downtime миграции (для обратно совместимых изменений).
- История изменений схемы хранится в Git вместе с кодом.
- Автоматическое применение при деплое — нет ручных шагов.

**Негативные / риски и их смягчение:**
- *Деструктивные миграции* (DROP COLUMN) необратимы без резервной копии.
  → Смягчение: бэкап PostgreSQL выполняется каждые 2 часа; перед деструктивной миграцией — ручной бэкап.

## ADR-009: Ruff в качестве линтера и форматтера

### Статус
Принято

### Контекст
Команда нуждается в едином стиле кода и раннем обнаружении ошибок. Рассматривались: flake8 + black + isort (раздельные инструменты), pylint, ruff.

### Решение
Выбран `ruff` (конфигурация в `ruff.toml`) — единый инструмент, заменяющий flake8, black, isort и pyupgrade.

**Почему ruff:**
- В 10–100× быстрее flake8/black за счёт реализации на Rust.
- Единый конфигурационный файл вместо трёх-четырёх.
- Покрывает линтинг и форматирование одной командой (`ruff check`, `ruff format`).
- Легко интегрируется в pre-commit hooks и CI.

### Последствия

**Позитивные:**
- Мгновенная проверка кода даже на большом проекте.
- Единообразный стиль без дискуссий в code review.

## ADR-010: GitHub Actions для CI/CD

### Статус
Принято

### Контекст
Необходим автоматический запуск тестов, линтера и сборки образов при изменениях в репозитории. Проект уже размещён на GitHub.

### Решение
Используется GitHub Actions (`.github/workflows/`).

**Типичный пайплайн:**
- Запуск `ruff check` и `ruff format --check`.
- Запуск `pytest` с покрытием (`.coveragerc`).
- Сборка Docker-образов и публикация в `readmeivtyarsu` Docker Hub registry.
- (Опционально) деплой на prod-сервер по SSH при мердже в `main`.

**Почему GitHub Actions, а не Jenkins / GitLab CI:**
- Нативная интеграция с репозиторием — нет отдельного CI-сервера.
- Бесплатный лимит минут для публичных репозиториев.
- Готовые actions для Docker, Python, SSH.

### Последствия

**Позитивные:**
- Автоматическая проверка каждого PR — сломанный код не попадает в `main`.
- Образы собираются и публикуются автоматически — ручной `docker build` не нужен.

**Негативные / риски и их смягчение:**
- *Лимиты GitHub Actions* для приватных репозиториев.
  → Смягчение: репозиторий публичный; при необходимости — self-hosted runner.
- *Секреты* (Docker Hub credentials, SSH ключ) должны храниться в GitHub Secrets.
  → Смягчение: используются `secrets.DOCKER_PASSWORD`.

# ADR-011: Модель разработки — Scrum + Kanban с непрерывными релизами и живой спецификацией

## Статус
Принято

## Контекст
Проект использует текстовую спецификацию.  
В спецификацию вносят изменения **заказчик, менеджер и сама команда** в процессе разработки.  
Основные драйверы изменений:
- обнаружение несостыковок при реализации (разработчики);
- новые идеи и предложения от команды;
- обратная связь от заказчика;
- обратная связь от тестировщика (дефекты, неоднозначности требований).

Команда работает **недельными спринтами** для планирования задач.  
Релизы выпускаются **непрерывно**: по готовности новой функциональности или исправления критического дефекта.  
Регрессионное тестирование выполняется **после исправления дефектов** (не перед каждым релизом).

**Ограничения:**
- нужно поддерживать частые изменения требований;
- релизы не должны быть привязаны к концу спринта;
- тестировщик должен иметь право уточнять спецификацию по результатам своей работы.

## Решение
Выбрана гибридная модель: (scrum + kanban) недельные спринты + непрерывный поток релизов с **живой спецификацией**, управляемой тестированием.

**Как именно:**
- **Недельные спринты** используются только для планирования задач и ретроспективы, но **не блокируют релизы**.
- **Релиз** происходит мгновенно, как только:
  - завершена любая задача (фича) или исправлен критический дефект;
  - пройден регрессионный тест (автоматический или ручной для затронутой области);
  - спецификация (если менялась) обновлена и закоммичена в Git.
- **Спецификация** (`specification.md`) — единый источник правды. Изменения вносятся через Pull Request или прямое редактирование с уведомлением команды. 
- **Регрессионное тестирование** выполняется после каждого исправления дефекта (с фокусом на изменённые модули и критический путь).

## Последствия

**Позитивные:**
- Заказчик получает новые фичи и критические исправления без ожидания конца спринта.
- Неоднозначности спецификации выявляются и исправляются раньше (тестировщик — активный соавтор).
- Недельные спринты дают ритм и прозрачность для команды.

**Негативные / риски и их смягчение:**
- *Путаница в приоритетах*: заказчик может запрашивать «релиз прямо сейчас» сырой фичи.  
  → Смягчение: чёткое определение критериев готовности к релизу: спецификация обновлена, все автотесты пройдены, код слит в main.
- *Регрессионное тестирование только после дефектов* может пропустить побочные эффекты от новых фич.  
  → Смягчение: обязательный прогон автоматического smoke-теста перед каждым релизом (независимо от причины).
- *Частые изменения спецификации* дезориентируют новых членов команды.  
  → Смягчение: ведение истории изменений внутри с помощью трекера GitHub.
